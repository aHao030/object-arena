# 主流设备支持方案

日期：2026-11-10。状态：设计目标，尚未实现或真机验收。

用户要求：实时操控，并希望主流电子设备都能运行。第一版采用同一浏览器产品，优先覆盖电脑、手机、平板；设备能力决定画质，不改变比赛物理规则。智能电视、游戏主机、手表、车机及各类应用内浏览器不在首版参战保证范围，后续按使用需求补充。

## 支持范围如何成立

| 设备类型 | 第一版目标入口 | 操作与验收重点 | 当前结论 |
|---|---|---|---|
| Windows 电脑 | 维护中的 Chrome、Edge、Firefox | 键盘、鼠标、集成显卡与独显 | 待真机验证 |
| macOS 电脑 | 维护中的 Safari、Chrome、Firefox | Retina 分辨率、触控板、Apple Silicon 与存量 Intel | 待真机验证 |
| 常见桌面 Linux | 维护中的 Chrome / Chromium、Firefox | 显卡驱动、WebGL 上下文、文件选择 | 待真机验证 |
| Android 手机与平板 | 维护中的 Chrome；另选国内常用系统浏览器抽测 | 中低端 GPU、多点触摸、权限、发热降频、网络切换 | 待真机验证 |
| iPhone | 维护中的 iOS Safari | 小屏、安全区、系统打断、相机与相册 | 待真机验证 |
| iPad | 维护中的 iPadOS Safari | 触摸、外接键盘、横竖屏、分屏与动态视口 | 待真机验证 |

发布时记录实际 OS、浏览器版本、设备型号和通过日期，形成明确的最低已验证配置。桌面浏览器以发布时最新稳定版及前一稳定版为测试窗口；iOS/iPadOS 以发布时实际可获得的两个受维护系统主版本为测试窗口。没有通过的组合不能标为“已支持”。版本号不是能力检测的替代品，不能由 User-Agent 判断设备一定能参战。

## 技术基线与降级

1. 大厅、资产清单、费用和任务状态采用普通响应式页面。比赛使用 WebGL2；启动前创建真实上下文、试绘制、加载解码器，并检测持续 WebSocket 连接。WebGL2 已广泛提供，但硬件、驱动和浏览器策略仍可能使创建失败。[MDN WebGL2](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext)
2. 采用当前 three.js 的 WebGLRenderer 时，WebGL1 不能作为低端降级路径，因为其自 r163 起不再受支持。WebGL2 失败时保留非比赛页面，说明原因并提供重新检测；不显示永远加载的黑屏。[three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)
3. WebAssembly 用于客户端物理预测或资产解码；启动自检实际加载锁定构建，首发比赛要求通过，无预测设备只保留非比赛页面。未来放开无预测参战必须先做弱网/手感验证；服务器负责权威物理。[MDN WebAssembly](https://developer.mozilla.org/en-US/docs/WebAssembly)
4. WebGPU、Wasm 多线程、SharedArrayBuffer、OffscreenCanvas 和桌面安装均不作为首版必需条件。WebGPU 留作未来画质增强，关闭后核心流程仍须完成。[MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)
5. 拍照入口部署 HTTPS，只在用户点击后请求相机，不请求麦克风；拒绝、设备缺失或用户一直未回答权限请求时，仍可选相册或文件。拍照结束即停止相机轨道。[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

## 画质档位

下列数值均为初始预算与待测目标，不是已测性能。按真实帧耗时自动降档，也允许玩家手动选择；不要依据售价、品牌或浏览器内存接口分类。

| 项目 | 省电档 | 标准档 | 高画质档 |
|---|---|---|---|
| 稳态显示目标 | 30 FPS | 60 FPS | 60 FPS |
| 像素比例上限 | 1 | 1.5 | 2 |
| 单物体可见三角面预算 | 10,000 | 30,000 | 60,000 |
| 贴图最长边目标 | 512 | 1,024 | 2,048 |
| 阴影 / 后处理 | 简化接触阴影 / 关闭 | 有限阴影 / 少量 | 有预算的阴影 / 可选 |
| 首局所需下载预算 | 不超过 15 MB | 不超过 25 MB | 不超过 40 MB |

数字限制应用于处理后的比赛资源，不能据此推断原始上传大小可无限制。总场景预算必须合计双方、场地、界面及解码峰值。原图、原网格和全部 LOD 不应同时驻留；提前加载下一档必须受缓存预算限制。移动端持续参战 20 分钟需要单独测发热和降频。WebGL 没有跨设备可靠的显存总量查询，内存预算应由受控资源大小和真机测试共同约束。[MDN WebGL 最佳实践](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

每一比赛物体的碰撞体、尺度、质量、惯量、摩擦、恢复系数和驱动约束在所有画质档完全相同。视觉 LOD 不得悄悄改变轮廓判定。试穿透视的碰撞体预览要在各档都可用；低画质不隐藏具有判定意义的场景元素。

## 键盘与触屏

- 电脑使用可重绑键位；触屏使用屏幕摇杆和同等功能的动作按钮。控制都转换成相同的归一化输入，再由服务器应用同一力、力矩和功率上限。
- 油门与转向为独立[-1,1]控制轴，不做单位圆归一化。键盘可同时满油门满转向，触屏使用方形映射摇杆或独立滑杆，也必须能达到(1,1)；提供数字方向按钮。服务器统一限制总功率、牵引和能量，不提供只在一端存在的自动动作。
- 桌面 / 触屏混合匹配先提供休闲验证。竞技开放之前比较不同输入模式的胜率、操作失败和延迟；性能不足时改善控制或提供输入偏好匹配，不能宣称不同设备天然公平。
- 交互按钮的触摸区域以至少 44×44 CSS px 为设计目标，避开系统边缘手势及刘海安全区；支持左右手调整和文字缩放。界面用文本或形状同时表达状态，不能只靠颜色、声音或震动。
- 横屏优先，竖屏也可完整操作与退出。旋转、分屏、来电、指针取消、页面失焦及摇杆外松手时必须发送归零输入；服务器还须有独立输入超时，不能依赖该消息一定送达。
- 比赛镜头提供一致的有效视野，宽屏只能增加非判定界面空间。禁止宽屏玩家比竖屏玩家获得额外战场信息。

## 网络与系统打断

默认目标为 1v1、每局最多 120 秒、服务器固定 60 Hz、快照 20 Hz、输入 30 Hz；数值需由原型和负载测试验证。客户端显示帧率不控制仿真步数。首版不在同一场比赛中按单个客户端性能降低物理精度。

推荐上线网络档位：RTT 不超过 100 ms、抖动不超过 20 ms、丢包不超过 1% 时完成标准验收；RTT 150 ms / 抖动 30 ms / 丢包 2% 为降级测试。上述均为测试条件，不是所有网络的服务承诺。匹配前显示网络状态，严重不稳定时建议训练模式，并允许退出匹配。

浏览器进入后台可能停止绘制、节流定时器；WebKit 在 iOS 上还可能挂起页面。因此手机切后台不能继续后台操控，也不能暂停对手。[MDN 页面可见性](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)、[WebKit 后台节能机制](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/)

服务器无新输入250ms后归零驱动力，对象继续受重力、惯性和碰撞影响。累计失联预算每人每局15秒，心跳超2秒或连接断开触发失联并回溯最后有效心跳；重连不重置累计预算。返回后取完整权威快照和输入序号基线，清空过期输入；期间满足胜负条件照常结束。[Colyseus Rooms](https://docs.colyseus.io/room)

监听 WebGL 上下文丢失，出现后停止呈现过期画面并提示恢复；恢复成功重新加载资源并取权威快照，失败则允许回大厅。客户端图形故障不触发全局暂停或无效局，按普通断线规则处理。上下文丢失可以用测试扩展主动模拟。[MDN webglcontextlost](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextlost_event)

iOS 网页可能因系统内存压力被回收；历史 WebKit 工程师说明中也区分设备与系统压力，不能把某个固定 GB 数字当成所有 iPhone 的永久保证。本项目由小资源、及时释放和恢复流程降低风险，并以真机测试验收。[WebKit 内存问题说明](https://bugs.webkit.org/show_bug.cgi?id=277848)

## 发布前真机清单

至少包含一台集成显卡 Windows 电脑、一台 Mac、一台 Linux 桌面、一台中低端 Android、一台主流 Android、一台存量 iPhone、一台当前 iPhone、一台 iPad。每台完成首次访问、拍照或文件导入、确认物理卡、训练、跨端对战、断线重连及再次进入，并连续运行20分钟。此清单是覆盖下限，不代表覆盖所有主流设备。

发布支持表需写“型号 / OS / 浏览器版本 / 档位 / 冷启动时间 / 1%低帧或帧耗时分位 / 峰值资源 / 断线恢复 / 验收结果 / 日期”。模拟器只能补充检查，不能取代真机 GPU、温控、相机和系统打断测试。第一版推广用语应为“支持已验证的主流电脑、手机和平板浏览器”，不能写“任何电子设备都能流畅运行”。
